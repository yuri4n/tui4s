```sbt [build.sbt]
libraryDependencies += "io.github.yuri4n" %% "tui4s-core" % "<version>"
```

::warning
tui4s is under construction. No version is published yet.
::

`tui4s-core` gives the runner, `TuiApp`, the composables, the widgets and the headless test kit in one dependency. `TuiApp`, `tui4s.use` and `tui4s.widgets` are in the core jar. The POM also depends on tui4s-runner and tui4s-testkit. Each published artifact has its own version.

| Artifact | For |
| --- | --- |
| `io.github.yuri4n::tui4s-core` | An app: `TuiApp`, the composables and the widgets, plus tui4s-runner and tui4s-testkit. |
| `io.github.yuri4n::tui4s-runner` | The terminal runner for kyo-ui: `Tui.run`, the components (`Hooks`, `Component`), the screen types. |
| `io.github.yuri4n::tui4s-testkit` | `tui4s.testkit.Headless`, the headless test kit. |

There is no ZIO or Cats Effect module. Issues [#18](https://github.com/yuri4n/tui4s/issues/18) and [#19](https://github.com/yuri4n/tui4s/issues/19) track them.

A library, or a main of its own with no `TuiApp`, can use the runner alone. Then add the test kit in the `Test` scope:

```sbt [build.sbt]
libraryDependencies += "io.github.yuri4n" %% "tui4s-runner"  % "<version>"
libraryDependencies += "io.github.yuri4n" %% "tui4s-testkit" % "<version>" % Test
```

tui4s-core, tui4s-runner and tui4s-testkit use the same packages (`tui4s`, `tui4s.use`, `tui4s.widgets`, `tui4s.spi`, `tui4s.testkit`), so the imports do not change.

## Requirements

- **JDK 25.** Kyo 1.0.0-RC7 needs JDK 25 to compile and to run. Make sure that `java -version` shows 25.
- **Scala 3.9.0** or later.
- **A deep compiler stack.** Kyo's inline for-comprehensions need it. Put this line in the `.jvmopts` file at the root of the build:

```text
-Xss16m
```

## Platforms

CI checks the real terminal path on Linux, with a pseudo-terminal (the PTY kit). CI does not check other platforms. Windows is experimental. tui4s reads the keyboard, a paste and a resize. It does not read the mouse.

## Versions

Each module has its own version and its own release tag (`<module>-v<version>`). The versions follow early semantic versioning: `0.y.z` to `0.y.(z+1)` is binary compatible, and `0.y` to `0.(y+1)` can break binary compatibility.

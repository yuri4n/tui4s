## Problems and decisions in this PR

- The carried `TuiApp` (the old model) does not compile against the new API, so 4a (TuiApp) comes before the strict-flag step 3; step 3 needs 0 line changes (0 warnings in CI mode after 4a and the adapt commit).
- The stop by the JVM: on SIGTERM the restore hook of the session can end the run as a quit (a closed inbox is `Msg.Quit`) before the stop hook interrupts it. PR 5 then ran `onExit` and printed "interrupted" in a race with the halt of the JVM. Now `runMain` asks `internal.Hooks.shuttingDown` (the JVM refuses a new hook while it runs its hooks: a probe hook is added and removed) and then prints nothing and skips `onExit`. `runMain` returns 1 then, and `main`'s `System.exit(1)` blocks until the JVM halts with its own code (143, 130, or the code of a `System.exit` in the app). The PTY kill rows see `EXIT=143` and `EXIT=130` right after the restore, with nothing between. A `Scope.ensure` of the app may not finish before the JVM exits on a signal (the restore is what the stop hook waits for); the Scaladoc of `ui` says that it runs after a quit.
- The task's leaf "a failing ui or handler -> 1": a UI that fails gives 1 (its stack trace and cause after the restore); a handler that fails does NOT end the run (C3: it is logged and the run goes on), so its leaf checks the log line after the restore and the exit code 0 after `q`.

The print key of the test app uses `System.out.println` (always captured), not Scala's `println`.

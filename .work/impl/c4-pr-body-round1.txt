After the merge, a tui4s app has components in two styles. Hooks (`tui4s.Hooks`): a component is a function with `useSignal`, `useHold`, `useFold`, `useEffect` and `useInterval`, and `component(key)(body)` is a node that the runner mounts (the body runs at the mount, in a `Scope` that closes at the unmount). The class style (`tui4s.Component`): a `State` type member, `initial`, `view(state)` and `onMount(state)`; the runner keeps the state under the position and the overridable `stateKey` (the class name by default). The runner's component branch, which C2 cut from the carried prototype, is back (`World.comps`, `World.pending`, `Source.Comp`, `Mount.mountComponent`, `gcComps`, the pending wait of the settle), with `TuiOptions.pendingTimeout` (a `java.time.Duration`, 2 s). Every fiber that a component mount or a hook starts joins the live-fiber gauge of the run and ends with the run (R1 option b). Five bugs of the prototype's component code, found by the new tests, are fixed in their own commits, each with a regression test and a negative control (P-6). The CounterStyles fixture (both styles) runs in the core tests; the runnable example is T2's. Base: PR #14 (T1, `feat/kyoui-04-terminal`) at 0893800.
